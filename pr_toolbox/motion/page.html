What the maintainers plan for each area of the code, which open pull requests are changing it, and what merging any one of them does to the others. Look up a file or a PR before you start, so new work goes with the plan rather than against it.

Compiled by a community contributor from the repository and its public GitHub issues and pull requests. It is not an official %%PROJECT%% page. The targets are quoted from the project's own documents and the maintainers' issues, with links; everything else is counted by script.

Path forward

What to do next, in order

Each step makes the next one cheaper. New PRs come last on purpose: review time is what limits the project, so the most useful work starts with what is already open.

Triage

Every open PR, filtered by what a merge needs

Combine filters to narrow the list. "Nothing blocking" keeps PRs that are out of draft, merge onto %%BASE%%, pass CI, conflict with no other PR's code, break nothing these checks can see, add nothing the plan is retiring, keep the version number and caps whole, and have no changes requested by a maintainer. It is not a review: whether a PR is right is still a reviewer's call. Select a row for its full card.

Before you start

The rules every area shares

Areas

Where the code is going

Each area: the target as its owners wrote it, what to know before building there, the issues that plan it, the open PRs changing it, and counts taken from each release.

Conformance

The standards the project answers to

Each standard: whether it is certified, the code that carries it, the official tool that tests it and whether that can run before a merge, what the pending rule would change, and the open PRs touching it. Matched by files and titles, so it says what a PR touches, not whether it conforms.

Same work twice

Open PRs that overlap

Two PRs that fix one issue, add one name, or sit on top of each other. Reviewing one first, or combining them, saves a review.

Merge view

What merging does to the others

Each open PR merged onto %%BASE%% in memory, then every pair that shares a file merged on top of that. Mechanical files are %%MECH%%.

Releases

What each release removed

Global functions in library/ and interface/, class files in src/, and deleted files, between consecutive tags. Module authors: these are the names a module could still be calling.
